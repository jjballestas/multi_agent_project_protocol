Metodología employee-ready + evidencia publicable · Autor: Operador (John Ballestas), redactado por el asesor con autoridad delegada · 2026-07-02 · Estado: APROBADO POR EL OPERADOR (GO 2026-07-02) · Formalización en ledger: pendiente (DECISION en el hub)

1. Contexto y motivación

  • La empresa es el objetivo real. El operador tiene una empresa con empleados desarrolladores en otro país y necesita construir la suite Nova (Budget → Accounting → Payroll → Treasury, software financiero) usando su metodología de gobierno multi-agente.
  • El fork Hermes (Zeus-Aegis) está muerto como producto: 1.094 archivos ajenos vs 13 propios, treadmill de upstream, y contradecía la identidad. No se compite contra Claude Code / Codex / VS Code / Antigravity.
  • El activo diferencial (validado por 2 rondas adversariales internas + 5 externas, 0 NO-GO): la única implementación de referencia operativa del ciclo completo multi-agente (task→claim→delivery→review adversarial→close) con checker independiente, corpus longitudinal real (3.200+ eventos atestados) y mediciones pre-registradas.
  • El TFM no es formal — la publicación no depende de ninguna universidad.
  • Identidad de producto (frase canónica ratificada): "para desarrolladores profesionales — y para profesionalizar a quien construye software con IA sin serlo."

2. Decisión: dos carriles con prioridad explícita

CARRIL A — PRINCIPAL Metodología lista para empleados + Nova Budget como piloto instrumentado. Doctrina primero, instancia limpia distribuible, estudio pre-registrado (Q1–Q5). El retorno económico principal del sistema.

CARRIL B — SECUNDARIO, GATEADO "Publicar para ser reproducido": paquete reproducible + spike DSSE/Rekor + outreach institucional. Presupuesto duro: ≤1 día/semana del operador, con pausa automática si lo excede. El resultado modal aceptado sin eufemismos: credibilidad y capital de carrera.

Regla de subordinación: si en una semana el Carril B compite con un gate del Carril A, gana el A.

4. Secuencia: doctrina primero, instancia después

Es obligado por las propias reglas del sistema: (1) las features nunca se desarrollan en Nova (acoplamiento unidireccional, DECISION-0035/0049/0050); (2) la instancia nace de un release — si la doctrina no está en él, tocaría upgradear a mitad del estudio, contaminándolo; (3) para que "la metodología reduce defectos" signifique la metodología completa, la doctrina opera desde la tarea 1.

8. Riesgos principales

  • R7 Adopción interna falla — la metodología debe estar "aburrida de confiable" antes de los empleados (SLO interno como gate de arranque; onboarding ≤1 día).
  • R8 La presión de entrega corrompe el estudio — válvula de presión pre-registrada; publicar el período completo.
  • R9 La atención del operador es el cuello — gate de calendario duro: sprint 1 = 30 de julio; si algo se atrasa se recorta alcance, nunca la fecha.
  • R6 nolabs/nono absorbe el diseño sin atribución — DOI/fechas antes del contacto; petición decidida de antemano (perfil multi-agente OpenSSF, no PR de plomería).
