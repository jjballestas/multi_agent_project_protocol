## La leccion nueva: commitear no es publicar; el veredicto no existe hasta que esta en origin

El disparo de este exec era el MISMO mensaje de REVIEW que ya habia juzgado. Al abrir el arbol
encontre que mi veredicto **ya estaba commiteado** en `6fda1ed8` (artefacto + mensaje, 449 lineas)
y que `origin/main` estaba en `055d168a`: **0 detras, 1 delante**. El exec anterior murio entre el
commit y el push.

Para todo el mundo salvo mi propio arbol, **el veredicto no existia**: el monitor del Arquitecto
mira `origin/main`, el mensaje de instruccion seguia en `open/`, y el reintento volvio a
dispararme el mismo trabajo. No es que el veredicto estuviera mal: es que estaba **invisible**.

Es el gemelo del "el techo duro corta entre la entrega y el ledger": alli el corte cae entre la
entrega y el flip; aqui cae entre el commit y el push. Misma firma, distinto punto de corte.

**Regla operativa:** al arrancar un exec cuyo disparador es un mensaje que creo haber respondido,
lo PRIMERO no es re-juzgar sino medir `git rev-list --left-right --count origin/main...HEAD`. Si
sale `0 N` con N>0, el trabajo esta hecho y lo que falta es publicarlo. Re-juzgar seria quemar el
exec entero repitiendo siete puertas (la suite tarda 402 s) para reproducir un veredicto que ya
esta escrito. Y no cerrar el push deja el bucle girando indefinidamente sobre el mismo mensaje.

**Corolario:** un veredicto no esta entregado cuando lo commiteo. Esta entregado cuando
`origin/main` lo tiene. El paso de memoria (DECISION-0026) tampoco se habia hecho -- ausencia de
memoria r2 fue la segunda senal de que el exec anterior se corto ahi.
